## Owner clarification / bounded scope

Owner clarified that `Replicated due to Common support` means an otherwise unchanged row inherits a visible replication remark when a sibling row belonging to the same common Civil support has any real generated remark. Example: for `SL-101 Line 1` and `SL-101 Line 2`, if Line 2 has a generated `Load change`, `Support Type Changes`, relocation, or another visible comparison remark, unchanged Line 1 receives `Replicated due to Common support`.

This leg implements only that common-support propagation semantics. Target `REMARKS (IF ANY)` remains oracle-only and is blanked before production comparison. The rule cannot use target oracle text as production evidence.

## RCA

The prior implementation conflated structural common-support lineage expansion with Owner-visible remark propagation: `COMMON_SUPPORT_REPLICATED` from 1->N lineage could render `Replicated due to Common support` directly. That is not the Owner rule.

Real R2->R3 tracing showed the intended recipient `SL-111012(REF)||BWGA-1000-2"-B1110103-11503-01` has no material/user-visible local comparison change. It does have audit bookkeeping (`PRIMARY_MEMBER_RENUMBERED` and `SUPPRESSED_FIELD_CHANGED`). Its same-Civil sibling `SL-111012(REF)||BWGA-1000-2"-P1110105-256620-01` independently generates `Support Relocated`.

An initial broad unchanged-sibling implementation also exposed a false positive on `SL-111069(REF)||BWGA-1000-3/4"-D8310024-253461P1-01`. Non-oracle graph evidence showed that row is component/reference-only and lacks independent coordinate/load/count/description payload. The recipient gate therefore requires an exact continuing Civil+PIPE predecessor and independent active non-component engineering payload.

## Production correction

New typed event `COMMON_SUPPORT_REMARK_REPLICATED` is added after direct comparison events are known. It is emitted only when all of the following are true:
- at least two target locations share the same normalized Civil support family and have distinct PIPE identities;
- another sibling has a direct generated target-side remark;
- the recipient itself has no direct visible remark and no material blocking event;
- audit-only `PRIMARY_MEMBER_RENUMBERED` / `SUPPRESSED_FIELD_CHANGED` events do not block an otherwise unchanged recipient;
- the recipient has independent active payload beyond component/reference evidence;
- exactly one non-ambiguous source predecessor retains the exact Civil+PIPE identity.

The event records trigger sibling nodes/rows/event IDs, exact predecessor lineage, shared persistent references, recipient evidence, and ignored audit event IDs.

Legacy structural `COMMON_SUPPORT_REPLICATED` remains graph/audit evidence only and no longer renders the Owner-visible replication remark. Replicated events are excluded as direct triggers, preventing propagation cascades.

The comparison engine now augments the ledger in this order after direct events: line-identity shell -> total-support-point events -> common-support sibling remark propagation -> remark rendering.
